# 我借此火博客发布

将用户提供的内容整理成仓库中的文章，按用户要求交付草稿、提交或正式发布。先核对当前源码，再沿用现成发布链路。

## 定位项目与任务范围

- 生产网站：`https://wojiecihuo.cn`；仓库：`zszz3/blog`；生产分支：`main`。
- Skill 随仓库存放于 `.agents/skills/wojiecihuo-blog-publish/`。从全局 Skill 目录通过符号链接调用时，先解析实际文件位置定位仓库；其他机器或 worktree 中，用 `git rev-parse --show-toplevel` 和 Git remote 确认仓库，不把当前工作目录默认当成博客。以下命令均在博客仓库根目录运行。
- 先读当前 `AGENTS.md`（如有），检查 `git status --short`、当前分支和与 `origin/main` 的关系；保留已有改动，提交范围只包含本次工作。工作区有其他 Agent 的改动时，优先使用独立 worktree，不擅自清空或收进本次提交。
- “草稿、先预览、只整理、开 PR”按对应范围执行；“发布到博客、更新线上文章、上传到网站”包含提交到生产分支和验证上线。已有明确授权时继续执行，不重复确认。仅说“上传”且无法判断是保存原文件还是公开发文时，先整理可预览内容，再澄清公开范围。
- 用户只要求创建或修改本 Skill，不代表要新发一篇文章或改动服务器。

## 内容入口与约定

开始编辑文章时读 [内容与图片规则](references/authoring.md)。以当前 `src/content.config.ts`、`src/utils/article-model.ts`、`src/utils/article-cover.ts` 和 `docs/authoring/writing.md` 为准。

日常约定：

- 所有文章只放在 `src/content/posts/`，博客与文档共用一份内容。`docs/authoring/` 是维护说明，不是线上文章入口。
- 新文章通常为 `src/content/posts/<稳定目录名>/index.md`，图片随文章保存。更新旧文直接编辑原文件，保留原目录、文件名和首次发布日期，避免旧链接失效。
- 用 `views` 控制博客/文档入口；用 `series` 和非负整数 `order` 控制文档章节。不复制同一篇文章到第二处。
- 保留用户原文的意思、代码、表格、公式和来源。单纯上传不等于授权扩写、补造经历或改写结论。
- 填写真实简介、标签和分类。新文安排封面，优先复用用户提供的图片或正文中合适的图片；选图细节见内容规则。字数、阅读时间和首页标签由站点生成，不手填统计值。
- `draft: true` 不进入生产页面、搜索或 RSS，但提交到公开仓库的原稿仍可被读取。未来日期不是定时发布开关。

## 检查与预览

依赖按 `package.json` 的 `packageManager` 和工作流里的 Node 版本准备；目前为 Node.js 22.12+、pnpm 9.14.4。依赖未安装或锁文件发生变化时运行 `pnpm install --frozen-lockfile`。

正式发布前运行：

```sh
pnpm build
python3 scripts/verify_site.py
git diff --check
```

构建已包含 Astro 检查、静态页面和 Pagefind 索引生成。不要为了普通内容更新运行会全仓改写文件的 `pnpm format` 或 `pnpm lint`。修改文章路由、筛选或发布逻辑时，再执行相关现有测试；纯内容更新无需新造测试。

使用 `pnpm dev` 的实际输出地址预览草稿；正式输出可用 `pnpm preview` 检查。导入或版式发生变化时，在浏览器查看文章、封面、正文图片、代码/表格/公式及相关列表入口。纯小幅文字修改可用构建产物核对。检查生产产物中草稿被排除；`pnpm dev` 显示草稿是正常行为。

## 提交、发布和验收

需要提交、PR、正式发布或回退时读 [发布与验收](references/publishing.md)，按当次授权执行。

固定链路为：文章与图片进入 GitHub `main` → Actions 构建 → 增量传输 → 阿里云校验完整版本并切换。PR 只检查。已有发布器负责复用未变文件、SHA-256 校验和版本回退，日常发文不需要服务器 SSH 密钥或云控制台。

正式发布的完成条件：

1. 本次源文件已在生产分支，能定位到对应提交的 Actions 运行。
2. 该运行的 `build`、`deploy` 成功，`Publish complete release` 实际执行，发布回执中的提交与预期一致。整个运行显示绿色或 `deploy` 被跳过都不足以证明上线。
3. 正式域名的文章显示本次内容；按 `views` 检查博客/文档入口，核对图片、搜索和 RSS。首页只显示最近文章，旧文不在首页不一定是失败。

若检查或部署失败，保留原站点，修复已定位且属于当前任务的问题后重试；同一原因再次失败且没有新的修复依据时停止重复提交/重跑，报告具体阻塞。不要把重新建密钥、修改 SSH/防火墙、改部署开关或换托管平台当作普通发文步骤；基础设施问题交给单独的修复任务。

交付用简短中文说明文章链接、草稿或上线状态、提交/运行链接和实际检查结果。未完成上线就明确说明停在哪一步。
